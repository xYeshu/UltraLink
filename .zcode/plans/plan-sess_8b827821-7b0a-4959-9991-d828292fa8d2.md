## Two-way half-duplex chat (push-to-transmit + conversation log)

### Design principle
**Reuse the existing engine, don't fork it.** All modem logic (demod, packet build, compression, speed modes, waterfall, checksum) is reused unchanged. `sender.html` and `receiver.html` stay exactly as they are — zero regression risk. The chat feature is an **additive** new page (`chat.html`) plus a small chat-only script that layers on top of the engine.

### The architectural insight that makes it clean
The engine writes a received message to the DOM in exactly **one place**: the CHECKSUM-OK branch at `main.js:691` (`rxMessage.textContent = decodedText`). And sending happens through exactly **one** function: `sendMessage()`. Everything else is reusable plumbing.

So the chat layer is essentially: *intercept these two points* and mirror them into a conversation log. We do this without modifying the engine by giving `chat.html` the same element IDs the engine expects (so `main.js` binds normally) **plus** extra chat UI, then observing those elements.

### The half-duplex / feedback problem (and why push-to-transmit solves it)
If the mic is live while you transmit, your own speaker output feeds back into your own mic → you decode your own message. Full-duplex would need echo cancellation (unreliable on laptops). **Push-to-transmit sidesteps it entirely**: while the Transmit button is active, we pause the demodulator (stop listening), so you can't hear yourself. Release → you're receiving again. No collisions, no echo.

### Files to add
1. **`chat.html`** — unified page. Sections:
   - Header (same minimal style as other pages, "Chat" mode label)
   - **Conversation log** panel: scrollable, monospace, timestamped entries. Sent messages right-aligned (or marked with `→`), received with `←`. Persisted to `sessionStorage` so a refresh mid-conversation doesn't wipe history.
   - **Compose** section: text input (`id="txText"` so engine reuses it), speed-mode group (`id="speedMode"`), compression toggle (`id="compressToggle"`) — same controls as sender.
   - **Push-to-transmit** button (the key UX element). While held/active: stops listening, transmits, then auto-resumes listening on release. Shows clear state ("Listening…" / "Transmitting…").
   - A hidden/minimal receiver pipeline (frequency/bit/link-state readouts + waterfall) so you can see incoming bits, matching the receiver page.
   - Provides all element IDs `main.js` expects (`micStatus`, `detFreq`, `linkState`, `rxMessage`, `eventLog`, `scope`, `sendBtn` etc.) so the engine binds without modification.

2. **`chat.js`** (loaded after `main.js` on chat.html only) — the thin chat layer:
   - **History store**: array of `{dir: 'in'|'out', text, time}`, rendered into the log panel, mirrored to `sessionStorage`.
   - **TX interception**: wraps the `sendBtn` click. On transmit: call `stopListening()`, call the engine's send, then on `osc.onended` resume listening. Records the sent message to history.
   - **RX interception**: a `MutationObserver` on the `#rxMessage` element. When the engine writes a new decoded message there, append it to history. (This is the cleanest zero-engine-change hook — no need to touch `main.js`'s decode path.)
   - **Push-to-transmit state machine**: tracks whether currently transmitting; updates the button label and the link-state pill; prevents double-send.
   - Auto-starts listening on page load (with a user gesture for mic permission, since browsers require it).

3. **`index.html`** — add a fourth tile: "Chat" linking to `/chat.html`.

### Lifecycle of a half-duplex exchange
1. Both users open `chat.html`. Both click "Connect" once (grants mic, starts listening, waterfall spins up).
2. Both in LISTEN state. Waterfall shows silence.
3. User A types a message and **holds Transmit**:
   - `chat.js` calls engine `stopListening()` → mic off, demod paused (can't hear self)
   - engine `sendMessage()` fires the oscillator
   - on `osc.onended`: engine `startListening()` → mic back on, hunting for preamble
   - sent message appended to A's history as an outgoing entry
4. User B (still listening) decodes it via the normal engine path → engine writes `#rxMessage` → `MutationObserver` fires → appended to B's history as incoming.
5. Repeat. Turns are implicit: you just don't transmit while someone else is.

### What is NOT changing
- `main.js` — **untouched**. (We hook via DOM, not by editing engine code.)
- `sender.html`, `receiver.html`, `tone-generator.html`, `style.css` — untouched.
- Compression auto-detect, speed modes, waterfall, packet format — all reused as-is on the chat page.

### Edge cases handled
- **Browser autoplay policy**: mic/speaker need a user gesture. The "Connect" button provides it.
- **Self-decode**: prevented by design (demod paused during TX).
- **Simultaneous transmit**: if both hold Transmit, neither is listening, so neither decodes — harmless. Each just sees their own send fail to get an ACK (there's no ACK in this design; that's a future enhancement). Visually obvious because the waterfall stops on both.
- **Long messages**: 64-byte cap is inherited; chat history shows progress.
- **History persistence**: `sessionStorage` (cleared when tab closes) — deliberately *not* `localStorage`, so chat content doesn't persist forever on a shared machine. Matches the ephemeral nature of an acoustic link.

### Trade-offs / what this is NOT
- **No message delivery confirmation.** Half-duplex push-to-transmit has no built-in ACK. If you want confirmation, that's the ARQ feature from my earlier analysis — a separate follow-up. For now, the waterfall + link-state pill give visual confidence.
- **No retry on failure.** A garbled message shows a checksum mismatch in the log (the engine already logs this); the user re-sends manually.
- **Push-to-transmit, not push-to-talk.** You transmit a typed message, not live voice. (Voice over FSK at ~25 bps is impossible anyway.)
